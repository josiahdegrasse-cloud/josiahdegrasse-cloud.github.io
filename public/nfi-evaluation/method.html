NFI retrieval evaluation

What this establishes

This is a preliminary open-literature retrieval pilot, not an accuracy claim for NFI production answers. The frozen dataset contains 12 CC-BY abstracts and 48 AI-authored, source-derived questions. None has been reviewed by an NFI scientist. Six papers supply 24 development questions; six different papers supply 24 held-out questions. All documents remain searchable. Each split has 18 standalone questions and six deliberately referential follow-ups.

Labels and source groups were fixed before the first retrieval run. During browser QA, abstract HTML normalization was corrected to preserve mathematical less-than signs and inline typography. Labels, splits and ranking parameters were unchanged; the final artifacts and baseline use the corrected corpus. Development runs exposed duplicate-document votes and abstract filtering behavior. Held-out labels were not used to change ranking parameters. Repeated artifact-generation runs do not turn this small pilot into an independent replication.

Reproduce

pip install -e '.[dev]'
python -m rag_food.benchmark --split dev --output run.json --baseline benchmarks/dev-baseline.json
python scripts/provision_reranker.py /absolute/path/to/reranker
python -m rag_food.benchmark --split heldout --reranker /absolute/path/to/reranker --output heldout.json
python scripts/render_evaluation_dashboard.py benchmarks/results/dev.json benchmarks/results/heldout.json --output dashboard.html

The portable adapter runs the production chunker and search/ranking path with real, revision-pinned MiniLM ONNX embeddings, exact cosine search and BM25. Production uses pgvector HNSW and PostgreSQL ts_rank_cd, not this BM25 adapter. This experiment isolates ranking behavior; it does not measure production corpus coverage, approximate-index recall, concurrent load or hosted latency. A full production evaluation must rerun reviewed queries against that index.

Six configurations isolate semantic, lexical, hybrid, query-context and cross-encoder effects. Context resolution carries the previous user topic into referential questions; it is deterministic context expansion, not an LLM rewrite. No assistant-generated claims are used as context. The reranker is cross-encoder/ms-marco-MiniLM-L6-v2, revision 233902d25c440f23af6f7d6e94d2946bac0bee0a; provisioning records artifact hashes. The server does not download models on request.

Hybrid + context 24/24 0.958 0.969
Hybrid + reranker 20/24 0.785 0.797
Hybrid + context + reranker 24/24 1.000 1.000

The six scripted follow-ups explain much of context expansion's gain. This is an intentionally small diagnostic suite with one labeled relevant paper per question. Additional papers could also be relevant. Precision@3 is therefore not a scientific relevance assessment of every returned passage. The raw JSON retains all queries, expected/returned source IDs, metrics, timings, model revision, dataset digest and code digest. The dashboard exposes misses rather than hiding them behind averages.

The cross-encoder improved ordering for two context-enabled held-out cases but increased warm local latency. It remains off by default. Production enablement requires a representative, human-reviewed benchmark and hosted resource checks.

Human and model answer evaluation

python -m rag_food.answer_evaluation prepare --run benchmarks/results/heldout.json --dataset benchmarks/open-literature-v1.json --output answer-review.json
# Optional local Ollama judge. The selected model must already be installed.
python -m rag_food.answer_evaluation judge --tasks answer-review.json --model YOUR_LOCAL_MODEL --output judge.json
python -m rag_food.answer_evaluation score --tasks answer-review.json --human human.json --judge judge.json --output quality.json --max-hallucination .05

The review packet runs the production deterministic professional_cited answer builder. It does not evaluate the separate browser Llama writer. A human review file has kind: "human", a named reviewer, and one records entry per task:

{
  "caseId": "copy from task",
  "answerSha256": "copy from task",
  "claims": ["supported", "unsupported", "unverifiable"],
  "context_relevance": [true, false, false],
  "answer_relevance": 0.5,
  "rationale": "Explain each unsupported claim and any ambiguity."
}

Each claim label corresponds to a factual assertion in the actual answer; do not copy the three example labels literally. Review all visible prose, not just the opening summary. Context labels follow retrieved-context order. The CLI scores faithfulness, context precision, answer relevance and the share of unsupported/unverifiable claims. It reports human-versus-model differences larger than 0.2. These are differences between reviewers, not a claim that the model judge is calibrated. Claim-free answers have no faithfulness score.

Missing reviews, unknown case IDs, stale answer hashes, absent explanations, invalid scores or incomplete claim coverage cannot pass the human quality gate. The local judge retries failed/malformed responses at most three times and then fails the run. No human labels or judge results have been fabricated.

CI and release boundaries

RAG evaluation / retrieval-regression runs the development suite on pushes and PRs and fails on a metric decline greater than 0.02. It also refuses to compare different dataset hashes, splits, k values or embedding revisions. Results are retained as CI artifacts for 90 days. Make this status required in branch protection to enforce it at merge time; a workflow alone does not prove merge blocking. The held-out split is kept outside routine optimization CI.

The human answer-quality command is ready, but is not a passing production gate until real reviews exist. Do not wire empty annotations into CI. On a reviewed release, run the command against the exact answer packet, retain quality.json, and require that job before release. The default 5% threshold is an explicit example policy requiring NFI agreement, not a measured current hallucination rate.

Remaining evidence needed

  • NFI-reviewed queries, answer references and relevance labels on the real corpus.
  • Unanswerable, ambiguous, conflicting-source and natural multi-turn cases.
  • Human/model agreement measurements and documented disagreements.
  • Live PostgreSQL, authorization and production latency checks for the release.
  • Real report usage and failures over time; no 30-day operating record is claimed.

Run against the production index

scripts/evaluate_live_retrieval.py replays a reviewed dataset through the existing /api/search endpoint without modifying the index. Use real production document IDs in relevance labels. Supply NFI_EVAL_BEARER_TOKEN or NFI_EVAL_API_KEY through the environment, then run:

python scripts/evaluate_live_retrieval.py --url https://YOUR_RESEARCH_HOST --tenant-id YOUR_TENANT --dataset /private/reviewed-cases.json --output /private/live-results.json

The output records source IDs and scores, not document excerpts or credentials. It is a separate live-service measurement and is not interchangeable with the portable six-configuration ablation. No live results have been recorded for this release. A manual Reviewed answer quality workflow is also available; it requires actual review files and fails if they are absent, stale or over the threshold.
